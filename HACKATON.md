# OnlineConf

## MVP и модель данных

OnlineConf — отдельный backend-сервис и административная SPA на том же домене (`/admin/`). Настройки меняются без деплоя и применяются в течение минуты при работающих соединениях.

Миграции: `db/migrations/000011_onlineconf.up.sql` и `000011_onlineconf.down.sql`. Все новые таблицы находятся в схеме `onlineconf`.

### `configs`

Одна таблица хранит конфигурации и feature flags.

| Поля | Назначение |
| --- | --- |
| `id BIGSERIAL PRIMARY KEY` | Постоянный ID записи, используемый в исключениях и истории |
| `scope TEXT` | `frontend`, `gateway`, `auth`, `profile`, `matching`, `chat` |
| `name TEXT` | Имя из 1–64 символов: строчные латинские буквы, цифры, подчёркивания |
| `kind TEXT` | `flag` или `config` |
| `value_type TEXT` | `bool`, `number`, `string`, `array`, `json` |
| `value JSONB` | Значение; у флага boolean является мастер-выключателем |
| `rollout_percent SMALLINT` | Для флага обязательный процент от 0 до 100; для конфигурации `NULL` |
| `policy_id`, `stage_index`, `stage_changed_at` | Политика плавной раскатки, индекс этапа с нуля и время перехода; дополнительная функциональность |
| `client_visible BOOLEAN` | Можно ли передавать ключ и вычисленное значение продуктовому фронтенду; по умолчанию `false` |
| `description TEXT` | Описание для администратора |
| `version INTEGER` | Версия записи, начинается с 1, увеличивается сервисом при изменении |
| `created_at`, `updated_at`, `updated_by` | Время создания, изменения и ID автора последнего изменения |
| `deleted_at TIMESTAMPTZ` | Мягкое удаление; обычные запросы исключают такие записи |

Частичный уникальный индекс `(scope, name) WHERE deleted_at IS NULL` разрешает повторное создание имени после удаления. Новая запись получит новый ID, старые исключения к ней не перейдут.

БД проверяет соответствие `value_type` значению JSONB. Для `json` допустимо любое JSON-значение. У флага обязательно `value_type = 'bool'`. Проверки диапазонов известных параметров (например, лимита фото) выполняет сервис.

### Остальные таблицы

| Таблица | Поля и назначение |
| --- | --- |
| `flag_overrides` | `config_id`, `user_id`, `enabled`, `created_by`, `created_at`; первичный ключ `(config_id, user_id)`. Индивидуальное включение или исключение пользователя |
| `history` | `id`, nullable `config_id`, `entity`, `action`, `before JSONB`, `after JSONB`, `actor_id`, `created_at`. Аудит конфигураций, флагов, администраторов и политик |
| `admins` | `user_id` — первичный ключ, nullable `granted_by`, `created_at`. Пользователи с административными правами |
| `rollout_policies` | `id`, `name`, `stages SMALLINT[]`, `min_interval INTERVAL`, `requires_approval`, `created_by`. Основа дополнительной плавной раскатки |
| `state` | Единственная строка `id = 1`, положительная `revision BIGINT`. Ревизия общего снимка настроек |

Пользователи в существующем проекте находятся в `public."user"`, а не в `public.users`. Внешние ключи и права используют реальное имя.

`history.entity`: `config`, `flag`, `admin`, `rollout_policy`. `history.action`: `create`, `update`, `delete`, `grant`, `revoke`. Изменение исключений записываем как `update` флага, включая старые и новые исключения в снимки.

Для начальных сидов и первичной выдачи прав через скрипт `actor_id`/`created_by`/`updated_by` могут быть `NULL`: это системные операции. В HTTP-операциях автора всегда берём из проверенного контекста.

## Сиды

| Ключ | Вид и значение | Раскатка | Доступ фронтенду |
| --- | --- | --- | --- |
| `profile.location_map_enabled` | `flag`, `bool`, `true` | 100% | Да |
| `profile.max_photos` | `config`, `number`, `6` | Не применяется | Да |

Также создаём политику «Стандарт 1→10→25→50→100»: этапы `{1,10,25,50,100}`, минимальный интервал одна минута, подтверждение администратора обязательно. Сам механизм переходов — дополнительная фича; наличие таблицы не запускает его автоматически. К сидовому флагу политика пока не привязана.

Создание политики и обоих параметров сразу записывается в `history`. Начальная ревизия снимка — `1`.

## Транзакции изменения

Каждая операция изменения в сервисе выполняется в одной транзакции:

1. Заблокировать строку `onlineconf.state` через `SELECT ... FOR UPDATE`.
2. Прочитать текущее состояние и проверить права и ограничения.
3. Изменить запись; для конфигурации увеличить `version`, обновить `updated_at` и `updated_by`.
4. Добавить `history` со снимками до и после изменения.
5. Увеличить `state.revision` и выполнить commit.

Все писатели используют одинаковый порядок блокировок. Так проверка последнего администратора и конкурентные изменения работают согласованно. При чтении снимка данные и его ревизию читаем в одной согласованной транзакции.

Проверки сервиса: override разрешён только для активного флага; этапы политики строго возрастают и заканчиваются на 100; индекс этапа существует и соответствует проценту. БД уже проверяет диапазон элементов массива, отсутствие NULL и согласованность полей политики.

## Административный доступ

Администратор входит как обычный пользователь. JWT содержит его ID. `ADMIN_LISTS`, отдельные пароли админов, claim `is_admin`, `role` и `redirect_url` в ответе login для новой схемы не нужны.

На все `/api/v1/admin/*` ставим авторизацию и middleware проверки таблицы `onlineconf.admins`:

- Нет действующего JWT — `401`.
- Пользователь отсутствует в таблице администраторов — `403`.
- Есть запись — передаём управление хэндлеру с ID пользователя в контексте.

Отзыв и выдача доступа пишутся в `history`. Последнего администратора удалять нельзя: сервис проверяет количество администраторов в транзакции после блокировки строки `state`. Этот запрет ещё нужно реализовать в сервисе.

Первого администратора выдаём существующему зарегистрированному пользователю:

```bash
bash scripts/onlineconf/grant-admin.sh admin@example.com
```

Скрипт использует работающий PostgreSQL Compose-проекта `totallyswipes-microservices`. Для другого проекта:

```bash
PROJECT=my-project bash scripts/onlineconf/grant-admin.sh admin@example.com
```

Скрипт запускаем из копии репозитория с заполненными deploy/env файлами. Он ищет пользователя по email, добавляет администратора, записывает аудит и увеличивает ревизию в одной транзакции. Повторная выдача существующему админу ничего не меняет. Неизвестная почта приводит к ошибке без изменений. `granted_by` и `actor_id` при ручной выдаче — `NULL`, поскольку скрипт выполняется оператором БД вне пользовательской сессии.

## Персональная конфигурация для фронтенда

Возвращать каждому пользователю рассчитанный config — правильно. Отдельные полные копии настроек в БД для каждого пользователя не нужны: храним общие параметры, процент раскатки и персональные исключения.

`GET /api/v1/config` берёт ID из JWT. Возвращаем только активные `client_visible = true` записи. Например:

```json
{
  "revision": 1,
  "configs": {
    "profile": {
      "max_photos": 6
    }
  },
  "flags": {
    "profile": {
      "location_map_enabled": true
    }
  }
}
```

Фронтенд получает готовые boolean-флаги. Списки исключений, персональные правила других пользователей и внутренние параметры ему не передаются. Ответ персональный: `Cache-Control: private, no-store`. Секреты не помещаем в параметры с `client_visible = true`.

При вычислении флага:

1. `value = false` — выключено для всех, включая персональные включения.
2. При `value = true` и наличии override используем персональное значение.
3. Иначе вычисляем стабильную группу пользователя и сравниваем с процентом.

Алгоритм группы: SHA-256 от однозначно сериализованных `(scope, name, user_id)`, первые восемь байт как unsigned big-endian, остаток от деления на 100. Флаг включён, если группа меньше `rollout_percent`. Не используем случайное число на каждом запросе.

Значения обычных конфигураций пока общие, персонализация относится к флагам. Создание произвольного параметра не добавляет поведение автоматически: продуктовый код должен уметь его применять.

## Интеграция с продуктом

`profile.location_map_enabled` используется и фронтендом, и поиском на backend. Несмотря на scope `profile`, Matching должен получать этот ключ через внутренний контракт OnlineConf. Независимые дубли флага не создаём.

Если флаг выключен для пользователя, фронтенд скрывает карту и выбор города, backend выполняет поиск без фильтра по городу даже при наличии города в запросе. Сохранённый город из БД не удаляем. Отключение карты выполняет администратор; автоматическое определение неисправности пока не реализуем.

`profile.max_photos` показывает лимит на фронтенде и ограничивает добавление фото в Profile. Backend самостоятельно проверяет лимит, независимо от состояния кнопки на фронтенде.

## Кеш и обновление

Сервисы держат снимок в памяти и опрашивают OnlineConf каждые 15 секунд. Продуктовый запрос не обращается в PostgreSQL за каждым флагом. В небольшом MVP снимок может содержать все исключения.

Фронтенд запрашивает `/api/v1/config` при входе и каждые 15 секунд без перезагрузки страницы. При успешном обмене суммарная задержка двух опросов — примерно 30 секунд плюс время запросов; таймауты оставляют запас до одной минуты.

При ошибке обновления сохраняем последний успешный снимок и логируем ошибку. Если снимка ещё нет: `max_photos = 6`, `location_map_enabled = false`. Во время недоступности OnlineConf гарантировать применение нового значения за минуту невозможно.

Проверка административных прав в первой версии читает таблицу на каждом административном запросе. Внутренний backend OnlineConf не публикуем в обход проверки прав.

## Права и деплой

Роль `onlineconf_app` создаётся в `db/security/roles.sql`. В `grants.sql` она получает подключение к БД, USAGE схем, SELECT только `(id, email)` таблицы пользователей и права на собственные таблицы. История доступна только на SELECT/INSERT; конфигурации удаляются через `deleted_at`. DDL, superuser и доступ к паролям пользователей не выдаются.

Текущий деплой не требует `ONLINECONF_ENV` и не читает `onlineconf.env` при установке паролей. Шаблон `deploy/env/onlineconf.env.example` подготовлен для будущего сервиса. Загрузку env и установку пароля `onlineconf_app` подключим вместе с запуском OnlineConf.

Контейнер OnlineConf, его конфиг и маршрутизацию добавляем при реализации сервиса; текущие изменения подготавливают только БД и установку пароля роли.

Если старая версия миграции 000011 уже применена на нужной БД, замена файла не обновит её автоматически: потребуется отдельная следующая миграция. Не откатываем БД с данными без отдельного решения.
