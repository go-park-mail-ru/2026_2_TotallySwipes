# Микросервисы Totally Swipes

Рабочая архитектура по обсуждению от 18 ноября 2026 года. Документ описывает целевое разделение, а не уже выполненную миграцию. Названия RPC предварительные; открытые вопросы перечислены в конце.

Распределение существующих HTTP endpoints, предлагаемых gRPC-вызовов и текущих Go-интерфейсов описано в [карте API](api-map.md).

## Общая схема

### Обязательные требования задания

| Требование | Баллы | Применение к проекту |
|---|---|---|
| Минимум три сервиса, обязательно Auth | 7 | Четыре бизнес-сервиса: Auth, Profile, Matching & Meeting, Chat; Gateway отдельно |
| Единственный `go.mod` в корне репозитория | В составе требования к сервисам | Все сервисы, Gateway и сгенерированные контракты используют один Go-модуль; вложенные `go.mod` запрещены |
| Общение сервисов по gRPC | 3 | Внутренние сетевые вызовы — gRPC/Protobuf, включая доставку межсервисных событий; внешние HTTP API провайдеров и клиентский WebSocket сохраняются |
| Покрытие кода тестами не менее 60% | 5 | Проверять отчётом покрытия в CI; точный состав учитываемых пакетов и исключение сгенерированного кода согласовать с критериями проверки |
| Метрики всех сервисов и машин на одном дашборде Grafana | 5 | Запросы, ошибки и время обработки для всех сервисов и Gateway; CPU, память, диск машин |

Один корневой Go-модуль — обязательное ограничение, а не временное упрощение. Сервисы располагаются в отдельных каталогах со своими слоями и Dockerfile, собираются в отдельные бинарники/контейнеры. Контекст Docker-сборки — корень репозитория. Общий Compose описывает приложение и инфраструктуру. Разделение исходников не разрешает прямые импорты реализации одного сервиса другим.

### Метрики и проверка требований

Предлагаемый стек наблюдаемости: Prometheus собирает метрики, Grafana показывает их на одном общем дашборде с отдельными панелями и фильтром по сервису; node_exporter предоставляет метрики машин. Эти компоненты пока описаны как план, а не реализованная инфраструктура.

- Gateway: количество HTTP-запросов, ошибок и длительность по шаблону URL, HTTP-методу и статусу.
- Каждый gRPC-сервис: количество вызовов, ошибок и длительность по сервису, полному RPC-методу и gRPC status. Сбор через общие unary/stream interceptors; регистрировать их в каждом сервере.
- Chat: дополнительно HTTP handshake WebSocket, активные соединения, количество команд/ошибок и длительность обработки команд по типу. Длительность соединения не заменяет время обработки сообщения.
- Остальные HTTP endpoints сервисов, включая файлы, также учитывать. Не использовать пользовательские ID, произвольные URL, тексты ошибок и сообщений как labels: для HTTP брать шаблон маршрута, для gRPC — стабильное имя метода.
- Для машин: CPU, память, использование и доступность диска; метрики процесса Go могут дополнять, но не заменяют метрики хоста.
- Дашборд должен включать все четыре сервиса, Gateway и машины; один дашборд не означает одну общую сумму без возможности увидеть конкретный сервис.
- В CI формировать итоговый отчёт покрытия и контролировать порог 60%; дополнительно смотреть покрытие по сервисам, чтобы общий процент не скрывал непроверенный сервис. Требование 60% отдельно для каждого сервиса в предоставленной формулировке не указано.

У внутренних gRPC-сервисов нет REST URL: эквивалент разреза по маршруту — полное имя RPC вида `/package.Service/Method`. Соответствие этого представления формулировке задания «по урлам и методам» нужно подтвердить при согласовании дашборда. Общие инструменты метрик допустимо вынести в технический пакет, но каждый сервис обязан подключить их.

Четыре бизнес-сервиса: Auth, Profile, Matching & Meeting, Chat. API Gateway — отдельный инфраструктурный компонент. Внешний HTTP/JSON API и его поведение должны сохраниться. Внутренние вызовы — gRPC с контрактами Protobuf.

```text
Фронтенд → Nginx → API Gateway → Auth / Profile / Matching & Meeting / Chat
                                Auth → Profile
                                Matching & Meeting → Profile
                                Chat → Matching & Meeting
Фронтенд → Nginx → Chat (WebSocket)
```

Gateway преобразует HTTP-запросы и ответы в gRPC-вызовы и обратно. В нём остаются особенности внешнего транспорта: cookies, CSRF, HTTP-статусы, JSON DTO. Бизнес-логика и доступ к хранилищам принадлежат сервисам. WebSocket направляется через Nginx в Chat; детальный транспорт файлов ещё предстоит описать.

## Auth Service

### Ответственность

- Учётные записи: идентификатор пользователя, email, хеш пароля.
- Регистрация и проверка учётных данных при входе.
- Выпуск access- и refresh-токенов, refresh-сессии, ротация и отзыв сессий.
- Инициация создания незаполненной анкеты в Profile при регистрации.

Auth владеет учётной записью; Profile владеет анкетой. Их связывает стабильный `user_id`. Анкета не содержит пароль или refresh-токены.

### Как регистрация работает сейчас

В [AuthService.Register](../internal/service/auth_service.go) хешируется пароль и вызывается `UserRepo.CreateUser`.

В [UserRepo.CreateUser](../internal/repository/postgres/user_repository.go) в одной PostgreSQL-транзакции выполняются:

1. `INSERT INTO "user" (email, password_hash) ... RETURNING id`.
2. `INSERT INTO profile (user_id) ...` — создаётся пустая анкета.
3. Commit: пользователь и анкета сохраняются вместе; при ошибке транзакция откатывается.

Затем Auth открывает refresh-сессию и выпускает access-токен. Создание сессии происходит после транзакции: если оно не удалось, пользователь и анкета уже существуют. Сейчас создание анкеты выполняется репозиторием, отдельного сетевого вызова Profile нет.

### Целевая регистрация

```text
Gateway → Auth.Register
  Auth: проверка данных, хеширование пароля, создание user
  Auth → Profile.EnsureProfile(user_id)
    Profile: создание незаполненной анкеты, если её ещё нет
  Auth: открытие сессии, выпуск токенов
Auth → Gateway: результат регистрации
Gateway → клиент: прежний HTTP-ответ и cookies
```

`EnsureProfile` должен быть идемпотентным: повторный вызов для того же `user_id` возвращает существующую анкету, не создаёт дубликат и не очищает заполненные поля. Profile определяет недостающие поля анкеты; результат нужен для сохранения текущего ответа регистрации.

После разделения общей транзакции Auth и Profile не будет. Нужно обеспечить восстановление регистрации при сбое после создания user, включая ситуацию, когда Profile создал анкету, но ответ потерялся. Конкретный механизм сохранения состояния и повторов ещё не выбран. Повтор регистрации не должен выдавать доступ к существующей учётной записи только по совпавшему email.

### Вход и токены

- При входе Auth проверяет пароль. Для сохранения текущего поля `missing` получает состояние заполненности анкеты через Profile.
- Auth управляет выпуском и ротацией токенов. Gateway устанавливает и очищает cookies.
- Сейчас refresh отзывает старую сессию и создаёт новую пару токенов; при конкурентном refresh продолжает только вызов, успешно отозвавший сессию.
- Сейчас logout отзывает refresh-сессию. Это само по себе не означает немедленного отзыва уже выданного access JWT.
- Место проверки access-токенов и способ доверенной передачи идентичности между сервисами нужно согласовать отдельно. Клиентский `user_id` не может служить доказательством авторизации.

## Profile Service

Владеет анкетами и их версиями, фотографиями, тегами, ответами и результатами психологических тестов, сохранёнными фильтрами поиска и `user_location`. Выполняет географическую фильтрацию и геокодирование. Подписки входят в целевую ответственность; их контракт пока не разобран.

Profile определяет актуальную версию анкеты, её заполненность и доступность для показа. Отбор кандидатов по возрасту, полу, тегам, расстоянию и другим поддерживаемым условиям выполняется в его хранилище.

### Психологический тест и Big Five

- Выдаёт описание текущего теста: вопросы, варианты ответов и версию. Отображение выполняет фронтенд.
- Принимает и валидирует ответы пользователя.
- Рассчитывает Big Five пользователя по ответам на тест.
- Сохраняет ответы, результат и версию теста, к которой они относятся.
- Возвращает пользователю его результат и предоставляет Big Five сервису Matching по gRPC.

Текущие маршруты `/tests/current`, `/tests/{test_id}/results` и `/tests/results/me` закрепляются за Profile через Gateway. Правила подсчёта результата теста принадлежат Profile.

## Matching & Meeting Service

Владеет свайпами, мэтчами, формированием ленты, алгоритмом совместимости и интеграцией с Timepad. На текущем этапе помогает найти пересечение интересов по событиям, после чего пользователи договариваются о встрече в чате. Отдельный процесс подтверждения времени и места встречи пока не требуется.

### Мэтчи, суперлайки и право переписки

- Обычный лайк создаёт мэтч при взаимной симпатии.
- Для обычных лайков и дизлайков повторный свайп заменяет предыдущий: актуально последнее принятое действие. Если обычный лайк заменён дизлайком и у пары есть мэтч от взаимных лайков, этот мэтч удаляется и право отправки новых сообщений прекращается. Доступ к повторному свайпу нужно предусмотреть в интерфейсе.
- Суперлайк сразу создаёт мэтч и разрешает переписку обоим участникам без ожидания ответного лайка. Это целевое продуктовое правило, а не описание уже реализованного поведения.
- Суперлайк нельзя отменить или заменить последующим свайпом. Прекращение и возобновление общения регулируется блокировкой/разблокировкой, без отмены факта суперлайка.
- Отправитель суперлайка сразу переходит в чат с получателем. Первое сообщение необязательно: пустой чат сохраняется в списке чатов обоих пользователей, к нему можно вернуться позже. Получатель также может написать первым.
- Получатель видит и новый чат, и профиль отправителя в разделе «Симпатии» с пометкой суперлайка. Matching хранит факт суперлайка, инициатора и состояние просмотра уведомления; событие онлайн-доставки не заменяет это состояние.
- Повторы запросов и одновременные действия не должны создавать дубли мэтча. Правила повторного мэтча после его прекращения ещё нужно определить.
- Блокировки между пользователями принадлежат Matching. Блокировка запрещает отправлять сообщения собеседнику и получать новые сообщения от него; суперлайк не обходит блокировку. Разблокировка снимает запрет инициатора, но не отменяет встречную блокировку. При сохранившемся мэтче и отсутствии блокировок переписка снова разрешена. Исключение заблокированной пары из рекомендаций остаётся предлагаемым правилом.
- `CanMessage(sender_id, recipient_id)` проверяет действующий мэтч и отсутствие блокировки. Chat вызывает этот RPC перед каждой отправкой сообщения, включая голосовые и видеокружки.

Chat отвечает за переписку, Matching — за основание, по которому она разрешена. Подтверждение просмотра суперлайка и прочтение сообщения — независимые состояния.

### Изменение свайпа и согласованность мэтча

На этапе реализации суперлайка нужно исправить текущий `SaveSwipeAndMatch`: сейчас он обновляет свайп и только создаёт мэтч при взаимности, но не удаляет его после дизлайка. Наличие значения `super_like` в текущем коде ещё не означает реализацию описанных выше правил суперлайка.

Matching в одной транзакции с сериализацией действий пары должен:

1. Проверить предыдущий свайп: сохранённый суперлайк нельзя заменить обычным лайком или дизлайком.
2. Сохранить допустимое новое действие.
3. Определить основание мэтча: суперлайк хотя бы с одной стороны либо взаимные обычные лайки.
4. Создать/сохранить мэтч при наличии основания; удалить обычный мэтч, если после дизлайка взаимности больше нет. Дизлайк получателя суперлайка не отменяет мэтч от суперлайка — для прекращения общения используется блокировка.

Проверки должны учитывать оба направления свайпов, чтобы одновременные запросы не оставляли мэтч в неверном состоянии. Повтор того же запроса не создаёт дубликат. Способ хранения основания мэтча (явный признак или определение по свайпам) предстоит выбрать при реализации.

Удаление мэтча означает прекращение права новой переписки, но не автоматическое удаление сообщений из базы Chat. Физическое удаление строки мэтча либо сохранение неактивной записи, видимость истории и использование прежнего чата при повторном мэтче ещё требуют решения. Изменение состояния мэтча нужно надёжно передать Chat; право отправки проверяется через `CanMessage`.

### Timepad: пересечение интересов и переход в чат

Matching получает события Timepad, принимает выбор обоих участников и находит пересечение. Если общие события найдены, интерфейс предлагает перейти в существующий общий чат пары. Matching инициирует создание системного сообщения в Chat с упрощённым списком названий общих событий. Пользователи далее сами договариваются о времени и месте обычными сообщениями.

Предлагаемый внутренний вызов — `Chat.PublishEventIntersection(match_id, search_id, result_version, events)`. Названия событий сохраняются в сообщении как снимок результата, идентификаторы — для связи с событиями. Повтор доставки одного результата не создаёт повторное сообщение. Matching отвечает за вычисление пересечения, Chat — за сохранение и доставку системного сообщения. Системные сообщения могут создавать только доверенные внутренние вызовы, а не клиент от имени другого пользователя.

При временной недоступности Chat результат поиска остаётся в Matching; доставку нужно повторять, например через outbox. Поведение при отсутствии пересечения и повторном изменении выбора ещё предстоит уточнить.

### Модераторская блокировка аккаунта

Это отдельное состояние, не блокировка пары пользователей. Заблокированный модератором аккаунт не участвует в поиске, не находится через поиск и не может создать WebSocket-соединение. Profile учитывает этот статус при выдаче кандидатов, Chat — при подключении.

Владельца статуса и механизм его передачи ещё нужно определить; предварительный вариант — Auth как владелец состояния учётной записи. Закрытие уже открытых соединений, доступ по прямой ссылке к анкете и ограничения HTTP-операций при такой блокировке пока требуют отдельного решения.

### Расчёт совместимости

- Получает готовые Big Five пользователей из Profile по gRPC.
- Сравнивает характеристики двух пользователей и рассчитывает оценку их совместимости.
- Использует оценку при формировании рекомендаций и в других сценариях, где нужна совместимость.

Алгоритм совместимости принадлежит Matching. Вопросы теста, валидация ответов и преобразование ответов в Big Five принадлежат Profile.

```text
Ответы на тест → Profile → Big Five пользователя
Big Five двух пользователей → Matching → оценка совместимости
```

### Получение ленты

```text
Клиент → Gateway → Matching.GetFeed
  Matching → Profile.SearchCandidates(user_id, cursor, limit)
    Profile: загрузка сохранённых фильтров и координат пользователя
    Profile: поиск доступных анкет по условиям и географии
    Profile → Matching: пачка кандидатов + следующий курсор
  Matching: исключение уже обработанных пользователей по правилам ленты
  Matching: расчёт совместимости и формирование порядка выдачи
  Matching: при необходимости запрос следующей пачки
Matching → Gateway → клиент: страница ленты
```

Начальный вариант: передавать в Profile `user_id`, курсор и размер пачки. Фильтры и координаты уже принадлежат Profile, поэтому Matching не должен сначала получать их, чтобы отправлять обратно. Если появятся разовые фильтры запроса, контракт можно расширить.

Profile возвращает `ProfileWithBigFive`: анкету и Big Five, если тест пройден. Совместимость, `liked_me` и `match_id` в этот ответ не входят. Matching определяет входящие и взаимные лайки по своим свайпам, рассчитывает совместимость и создаёт мэтч с `match_id` при взаимном лайке либо суперлайке по правилам выше.

### Вкладка «Симпатии»: мэтчи и фильтрация

«Симпатии» показывает партнёров по существующим действующим мэтчам, а не все входящие односторонние лайки. Обычный мэтч основан на взаимных лайках; мэтч от суперлайка также отображается, хотя ответного лайка для его создания не требуется.

Вкладка использует `GET /api/v1/matches`, расширяемый фильтрами по имени, возрасту и полу (девушка, парень, любые). Отдельный внешний `/sympathies` для этого сценария не нужен. Фильтры вкладки не изменяют сохранённые фильтры поиска кандидатов для ленты. Для возраста предлагается диапазон включительно; точное сравнение имени, имена query-параметров и валидацию нужно закрепить в HTTP-контракте.

```text
Клиент → Gateway → Matching.GetMatches(фильтры, курсор, limit)
  Matching: выбирает ограниченную пачку своих действующих мэтчей
  Matching: получает user_ids партнёров и сохраняет связь с match_id
  Matching → Profile.GetProfilesBatch(user_ids, filter)
    Profile: отбирает доступные анкеты из переданных ID по имени, возрасту и полу
    Profile → Matching: profiles[] (ProfileWithBigFive)
  Matching: сопоставляет анкеты с мэтчами по profile.user_id
  Matching: рассчитывает совместимость, добавляет match_id и данные мэтча
  Matching: при необходимости добирает следующую пачку мэтчей
Matching → Gateway → клиент: страница «Симпатий» и курсор
```

Big Five самого пользователя Matching также получает из Profile, если он ещё не загружен: для этого подходит отдельный пакетный запрос без фильтра вкладки. Собственную анкету нельзя отфильтровать условиями поиска партнёров. При отсутствии теста сохраняется предусмотренное API отсутствие оценки совместимости.

Согласованная форма внутреннего контракта:

```proto
message GetProfilesBatchRequest {
  repeated int64 user_ids = 1;
  MatchFilter filter = 2;
}

message GetProfilesBatchResponse {
  repeated ProfileWithBigFive profiles = 1;
}
```

`MatchFilter` — имя типа в текущем proto; он содержит условия по данным анкет, а не проверку наличия мэтча. Поле типа message может отсутствовать без ключевого слова `optional`.

- Без `filter` Profile возвращает доступные анкеты из переданных ID; с фильтром — только подходящие.
- Profile не проверяет взаимность и не читает таблицу мэтчей. ID партнёров выбирает Matching.
- Ответ не содержит отдельного списка пропущенных ID: Matching не различает отсутствие/недоступность анкеты и непрохождение фильтра. Пустой список — успешный результат, а не ошибка; сбой сервиса передаётся gRPC-ошибкой, а не пустым списком.
- Порядок ответа Profile не определяет порядок мэтчей. Matching сопоставляет данные по `profile.user_id` и сохраняет свой порядок выдачи.
- Размер пачки ограничивается сервером. Все мэтчи пользователя одним неограниченным запросом не передаются.
- Пустая отфильтрованная пачка не означает конец списка мэтчей. Matching продолжает добор в пределах бюджета работы; нужны правила возврата частичной страницы и курсора при достижении этого бюджета.
- Курсор принадлежит Matching и учитывает обработанные мэтчи. Нельзя пропускать подходящие анкеты, оставшиеся в загруженной пачке за границей страницы. При смене фильтров клиент начинает просмотр с первой страницы.

Таким образом, `SearchCandidates` ищет новых кандидатов по данным Profile, а `GetProfilesBatch` получает/фильтрует известные Matching анкеты по переданным ID. Оба метода возвращают данные для расчёта совместимости, но не рассчитывают её.

### Пагинация и границы ответственности

Пачка Profile не равна странице ленты: после исключения свайпнутых пользователей кандидатов может не хватить. Matching отвечает за добор пачек и итоговый курсор ленты.

Внутренний курсор Profile и внешний курсор ленты имеют разный смысл. Нужно определить стабильный порядок, область ранжирования, обработку лишних кандидатов из пачки и изменения данных между запросами. Нельзя просто вернуть курсор конца пачки, если часть подходящих кандидатов ещё не выдана: они могут быть пропущены. Добор должен иметь ограничение по времени и объёму работы.

Matching не читает таблицы Profile напрямую. Profile не читает таблицы свайпов Matching. Существующие SQL-запросы, объединяющие эти данные, нужно переработать при миграции.

Допустим один экземпляр PostgreSQL с разделением схем или баз и прав доступа. Владельцем данных остаётся один сервис; другие обращаются через его API. Прямые межсервисные SQL-запросы могут быть только явно обозначенным временным этапом миграции.

## Chat Service

### Функциональность и доступ

- Чаты между двумя пользователями и их участники.
- Отправка текстовых сообщений, редактирование и удаление своих сообщений; точные ограничения операций предстоит определить.
- История переписки с пагинацией, позиции прочтения и количество непрочитанных.
- Голосовые сообщения и видеокружки: загрузка, метаданные и проверка доступа к файлам.
- WebSocket-доставка новых сообщений, изменений, удалений и обновлений прочтения.
- Reports пока под вопросом и не входят в подтверждённый объём функциональности; при добавлении предполагаемый владелец — Chat.

При отправке Chat определяет отправителя по авторизованному соединению, проверяет его участие в чате, затем запрашивает у Matching право переписки. При отказе сообщение не создаётся; при недоступности Matching возвращается временная ошибка. Одного участия в чате или открытого WebSocket недостаточно для отправки.

После суперлайка чат создаётся независимо от отправки первого сообщения и показывается обоим участникам. Предлагаемый механизм: Matching после фиксации мэтча вызывает `Chat.EnsureChat(match_id)` по gRPC; устойчивые повторы обеспечиваются outbox Matching. Chat идемпотентно создаёт чат и двух участников по `match_id`. Участники определяются по данным Matching, а не по произвольному списку из клиентского запроса. Повторный вызов возвращает существующий чат.

Фронтенд переводит отправителя в созданный чат. Если Chat временно недоступен, суперлайк и мэтч сохраняются, создание чата повторяется; интерфейс показывает временное ожидание/ошибку открытия, не требует нового суперлайка. Для обычного взаимного мэтча предлагается использовать тот же механизм создания чата.

### WebSocket и непрочитанные

После входа, успешной регистрации или восстановления авторизации при открытии вкладки фронтенд открывает одно WebSocket-соединение на вкладку для всех чатов пользователя. У разных вкладок и устройств могут быть отдельные соединения. Наличие мэтча не требуется для открытия соединения; модераторская блокировка аккаунта запрещает подключение. Блокировка отдельным собеседником не запрещает подключение.

Chat проверяет разрешённый Origin, access-токен, отсутствие модераторской блокировки и лимит подключений. Соединение связывается с проверенным `user_id`. Оно используется, пока вкладка открыта и авторизация действительна, но может оборваться раньше из-за сети или перезапуска сервера; фронтенд восстанавливает его и синхронизирует состояние. При выходе из аккаунта фронтенд закрывает соединение.

Под «живёт до refresh» принимается предлагаемый простой вариант: при обновлении токенов старое соединение заменяется новым с актуальным access-токеном. Сервер не оставляет соединение авторизованным после истечения access-токена. Refresh выполняется через Auth по HTTP; refresh-токен не используется как учётные данные WebSocket. Сохранение того же физического соединения после refresh потребовало бы отдельного протокола повторной авторизации и пока не закладывается.

Событие содержит `event_id`, тип и `chat_id`, по которому фронтенд обновляет нужную переписку. Сервер доставляет события только участникам соответствующего чата. Переключение между чатами не требует нового WebSocket; история загружается по HTTP через Gateway.

При входе и переподключении клиент получает актуальные чаты, непрочитанные и состояние открытой переписки из Chat. WebSocket передаёт дальнейшие изменения. Детальный порядок синхронизации должен исключать потерю изменений между загрузкой состояния и подключением к событиям.

Доставка сообщения не означает прочтение. Клиент явно подтверждает прочтение до конкретной позиции в чате; сервер проверяет эту позицию и продвигает её только вперёд. Изменение распространяется на остальные подключения пользователя. Блокировка одного собеседника не закрывает соединение для остальных чатов.

### Предполагаемое хранение

Ниже логическая модель, а не готовая SQL-миграция.

| Сущность | Основные данные | Хранилище |
|---|---|---|
| `chat` | `id`, уникальный `match_id`, время создания | PostgreSQL Chat |
| `chat_member` | `chat_id`, `user_id`, `last_read_seq`; уникальная пара чата и пользователя | PostgreSQL Chat |
| `message` | `id`, `chat_id`, `sender_id` для пользовательских сообщений, `seq`, тип (включая системный), текст/структурированные данные, время создания/редактирования/удаления, `client_message_id` | PostgreSQL Chat |
| `attachment` | `id`, `message_id`, ключ объекта, тип медиа, размер, длительность, состояние обработки | PostgreSQL Chat |
| `outbox_event` | `event_id`, тип, данные события, время создания, состояние и попытки обработки | PostgreSQL Chat |
| Медиафайлы | Голосовые сообщения и видеокружки | MinIO, отдельный bucket и права Chat |
| Временные состояния | «Печатает», присутствие | Память или Redis с TTL, если эти функции будут нужны |

`user_id` и `match_id` — межсервисные идентификаторы; Chat не читает таблицы Auth, Profile или Matching напрямую и не использует внешние ключи в их базы. Внутри собственной базы связи между чатами, участниками, сообщениями и вложениями проверяются ограничениями.

`seq` задаёт возрастающую позицию сообщения внутри чата, уникальную для пары `(chat_id, seq)`. `last_read_seq` хранит позицию прочтения участника; непрочитанные определяются по более поздним сообщениям собеседника с учётом правил удаления. Повтор отправки после обрыва соединения дедуплицируется по `(chat_id, sender_id, client_message_id)` и возвращает уже созданное сообщение.

Сообщения и история сохраняются независимо от онлайн-статуса получателя. Бинарные файлы не помещаются в строки сообщений. Chat проверяет права при выдаче медиа; наличие ключа объекта не должно само по себе давать доступ к переписке.

### События и надёжность доставки

Предлагается transactional outbox: изменение сообщения и запись события фиксируются одной транзакцией в PostgreSQL Chat. Фоновый обработчик отправляет событие активным подключениям и отмечает обработку; при сбое повторяет попытку. Повторы возможны, клиент учитывает `event_id` и версию/порядок изменений сообщения.

Outbox не является вечной второй копией истории и не подтверждает получение или прочтение сообщения пользователем. Обработанные события удаляются по политике хранения, которую ещё нужно выбрать. Для первой версии долговременный журнал событий на каждого пользователя не предполагается: после отключения состояние восстанавливается из чатов, сообщений и позиций прочтения.

Уведомление «вас суперлайкнули» принадлежит Matching и доступно в «Симпатиях» даже после офлайн-периода. Если его нужно доставлять по тому же WebSocket, предлагается передавать событие из Matching в Chat по внутреннему gRPC с устойчивой очередью outbox на стороне Matching и дедупликацией на стороне Chat. Chat в этом случае только доставляет уведомление; просмотр симпатии фиксируется в Matching. Точный контракт доставки ещё предстоит согласовать.

## Что ещё предстоит согласовать

- Восстановление регистрации после частичных сбоев и безопасные повторы.
- Точные RPC, поля сообщений и отображение ошибок на прежний HTTP-контракт.
- Проверка access-токенов, права доступа и передача идентичности по gRPC.
- Стабильная пагинация ленты, ранжирование, ограничения добора и поведение при изменении фильтров.
- HTTP-параметры фильтров «Симпатий», правила сравнения имени, порядок мэтчей и пагинация при доборе отфильтрованных пачек.
- Перенос текущих JOIN между профилями, свайпами и мэтчами на новые границы.
- Сохранение совместимости в существующих ответах API вне ленты.
- Поведение Timepad при отсутствии пересечения и изменении выбора; необходимость Reports, подписки и транспорт файлов.
- Ограничения редактирования/удаления сообщений, сроки хранения сообщений, медиа и outbox, лимиты и обработка медиа.
- Доступ к истории после блокировки или удаления мэтча; физическое/логическое удаление мэтча и судьба прежнего чата при повторном мэтче.
- Владелец модераторского статуса, закрытие активных WebSocket при блокировке и ограничения остальных API для заблокированного аккаунта.
- Синхронизация при переподключении, порядок событий, доставка между экземплярами Chat и гонка блокировки с отправкой сообщения.
- Контракт онлайн-уведомлений о суперлайке и правила повторного мэтча; лимиты суперлайков, если они предусмотрены продуктом.

При миграции проверяем не только сохранение URL, но и JSON-типы и поля, статусы и ошибки, cookies, CSRF/CORS, правила доступа и пользовательские сценарии. Этот документ пока фиксирует архитектуру; код приложения не изменяется.
