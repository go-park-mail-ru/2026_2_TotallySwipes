# WebSocket Chat

Планируемый контракт фронтенда и Chat Service. URL: `/ws` (`wss` при HTTPS). Одно соединение на вкладку обслуживает все чаты пользователя.

Авторизация — access-cookie; сервер проверяет токен, Origin и модераторскую блокировку. При истечении токена соединение закрывается, клиент выполняет HTTP refresh и подключается заново. `user_id` отправителя сервер определяет по авторизации.

## Команды клиента

Общая форма:

```json
{
  "type": "message.send",
  "request_id": "req-123",
  "data": {}
}
```

- `type` — имя команды.
- `request_id` — уникальный ID попытки запроса для сопоставления с ответом.
- `data` — поля команды.

### `message.send` — отправить сообщение

Текст:

```json
{
  "chat_id": "42",
  "client_message_id": "draft-456",
  "text": "Привет!"
}
```

Медиа:

```json
{
  "chat_id": "42",
  "client_message_id": "draft-457",
  "attachment_id": "attachment-10"
}
```

- `chat_id` — чат, участником которого является отправитель.
- `client_message_id` — ID сообщения клиента, сохраняемый при повторной отправке после сбоя.
- `text` — непустой текст; передаётся либо он, либо `attachment_id`, но не оба.
- `attachment_id` — готовое вложение, ранее загруженное по HTTP этим пользователем для этого чата.

Сервер проверяет участие, право переписки через Matching и содержимое; сохраняет сообщение с серверными `message_id` и `seq`. Повтор с тем же `(chat_id, sender_id, client_message_id)` возвращает сохранённое сообщение; иное содержимое с тем же ключом даёт конфликт.

**Ответ отправившему соединению:** `command.result` с `data: {chat_id, client_message_id, message}`. `message` — полный `ChatMessage`.

**События после создания:** `message.created` обоим участникам во все подключения; персональные `chat.updated` и, при изменении счётчиков, `chats.summary.updated` соответствующим пользователям.

### `message.edit` — изменить своё текстовое сообщение

```json
{"chat_id": "42", "message_id": "781", "text": "Привет, как дела?"}
```

- `message_id` — ID собственного неудалённого текстового сообщения.
- `text` — новый непустой текст.

Сервер проверяет авторство и правила редактирования; меняет текст, `edited_at` и `version`, сохраняя `seq`.

**Ответ отправившему соединению:** `command.result` с `data: {chat_id, message}`.

**События:** `message.updated` обоим участникам во все подключения; `chat.updated`, если изменилось превью карточки.

### `message.delete` — удалить своё сообщение

```json
{"chat_id": "42", "message_id": "781"}
```

- `message_id` — ID собственного сообщения.

Для этого контракта предлагается удаление у всех с сохранением позиции: `deleted_at` заполнен, `text` и `attachment` равны `null`; `version` увеличивается. Повторное удаление уже удалённого собственного сообщения успешно без нового изменения.

**Ответ отправившему соединению:** `command.result` с `data: {chat_id, message}`.

**События:** `message.deleted` обоим участникам во все подключения; персональные `chat.updated` и `chats.summary.updated`, если изменились превью или счётчики.

### `chat.read` — подтвердить прочтение

```json
{"chat_id": "42", "last_read_seq": 15}
```

- `last_read_seq` — позиция, до которой переписка действительно просмотрена включительно; загрузка или доставка сообщений не означает прочтения.

Сервер проверяет участие и допустимость позиции, затем сохраняет `max(текущая позиция, полученная позиция)`.

**Ответ отправившему соединению:** `command.result` с `data: {chat_id, user_id, last_read_seq}` и фактически сохранённой позицией.

**События при продвижении позиции:** `chat.read.updated` обоим участникам во все подключения; `chat.updated` пользователям, чьи карточки изменились, и `chats.summary.updated` читателю, если изменились его счётчики.

## Ответы на команды

Ответ получает только соединение, отправившее команду.

Успех:

```json
{
  "type": "command.result",
  "request_id": "req-123",
  "data": {
    "chat_id": "42",
    "client_message_id": "draft-456",
    "message": {
      "message_id": "781",
      "seq": 15,
      "sender_id": 104,
      "type": "text",
      "text": "Привет!",
      "attachment": null,
      "created_at": "2026-11-22T15:42:00Z",
      "edited_at": null,
      "deleted_at": null,
      "version": 1
    }
  }
}
```

Ошибка:

```json
{
  "type": "command.error",
  "request_id": "req-123",
  "error": {
    "code": "MESSAGING_NOT_ALLOWED",
    "message": "Отправка сообщений недоступна"
  }
}
```

- `error.code` — машинный код; клиент обрабатывает его, а не текст `message`.
- `error.message` — безопасное пояснение ошибки.
- `error.fields` — необязательный объект ошибок полей, как в HTTP API.
- При нечитаемом JSON или отсутствующем корректном `request_id` сервер возвращает `request_id: null`.

| Код | Значение |
|---|---|
| `VALIDATION_ERROR` | Некорректный JSON, тип команды или её поля |
| `CHAT_NOT_FOUND` | Чат отсутствует или пользователь не участник |
| `MESSAGE_NOT_FOUND` | Сообщение отсутствует в указанном доступном чате |
| `MESSAGING_NOT_ALLOWED` | Отправка запрещена правилами мэтча/блокировки |
| `MESSAGE_ACTION_NOT_ALLOWED` | Нет прав на редактирование/удаление или операция недопустима |
| `ATTACHMENT_NOT_AVAILABLE` | Вложение недоступно, не готово или не принадлежит отправителю/чату |
| `IDEMPOTENCY_CONFLICT` | `client_message_id` повторён с другим содержимым |
| `TEMPORARILY_UNAVAILABLE` | Временная недоступность зависимости |
| `INTERNAL_SERVER_ERROR` | Непредвиденная ошибка сервера |

Подтверждение отправки означает сохранение, а не доставку или прочтение. При неизвестном исходе отправки клиент повторяет её с прежним `client_message_id` и новым `request_id`.

## События сервера

Общая форма:

```json
{
  "type": "message.created",
  "event_id": "evt-900",
  "data": {}
}
```

- `event_id` — ID события для исключения повторов, не позиция сообщения.
- `data` — содержимое события.

### `message.created`

**Получатели:** оба участника, все их подключения.

`data: {chat_id, client_message_id, message}`.

- `message` — полный `ChatMessage` из [OpenAPI](swagger/openapi.yaml).
- `client_message_id` — ID для замены временного сообщения отправителя; `null` для системных сообщений.

**Клиент:** объединяет по `message_id`, собственный черновик сопоставляет по `client_message_id`, располагает по `seq`; в открытом пустом чате убирает приветственный блок. Отдельный GET на каждое событие не нужен.

### `message.updated` / `message.deleted`

**Получатели:** оба участника, все их подключения.

`data: {chat_id, message}` — полный актуальный `ChatMessage`, включая новую `version`.

**Клиент:** применяет только более новую версию; сохраняет позицию `seq`. Для ещё не загруженного сообщения запоминает обновление, чтобы последующий старый HTTP-ответ не восстановил старое содержимое.

### `chat.created` / `chat.updated`

**Получатели:** подключения каждого пользователя, чья карточка создана/изменилась.

`data` — полная персональная `ChatCard` из OpenAPI:

| Поле | Назначение |
|---|---|
| `chat_id`, `match_id` | Связь карточки с чатом и мэтчем |
| `peer` | Собеседник: `user_id`, имя, возраст, аватар |
| `is_new` | Пользователь ещё не открывал чат |
| `unread_count` | Актуальное количество непрочитанных сообщений |
| `last_message` | Превью последнего сообщения или `null` для пустого чата |
| `created_at`, `last_activity_at` | Дата создания и время активности для отображения/сортировки |
| `version` | Версия карточки именно для получателя |

**Клиент:** добавляет/заменяет карточку по `chat_id`, только если версия новее, и пересортировывает список по активности. У отправителя и получателя разные карточки; нельзя рассылать одинаковый `peer` и счётчики обоим.

### `chats.summary.updated`

**Получатели:** все подключения пользователя, чьи счётчики изменились.

```json
{
  "new_chats_count": 2,
  "unread_chats_count": 3,
  "unread_messages_count": 7,
  "version": 19
}
```

- `new_chats_count` — ещё не открытые чаты, включая пустые.
- `unread_chats_count` — чаты хотя бы с одним непрочитанным сообщением.
- `unread_messages_count` — общее число непрочитанных сообщений.
- `version` — версия сводки этого пользователя.

**Клиент:** заменяет счётчики при более новой версии; не прибавляет единицу и не вычисляет итог по частично загруженному списку чатов.

### `chat.read.updated`

**Получатели:** оба участника, все их подключения.

```json
{"chat_id": "42", "user_id": 105, "last_read_seq": 15}
```

- `user_id` — кто прочитал сообщения.
- `last_read_seq` — сохранённая граница прочтения включительно.

**Клиент:** продвигает позицию этого участника только вперёд; если читатель — собеседник, собственные сообщения с `seq <= last_read_seq` отмечаются прочитанными. Счётчики отдельно обновляются карточкой и сводкой.

## HTTP и синхронизация

- `GET /chats/summary`, `GET /chats/{id}` и `GET /chats/{id}/messages` дают начальное состояние; события поддерживают его актуальность.
- `POST /chats/{id}/seen` снимает новизну чата, но не подтверждает прочтение; сервер публикует карточку и сводку при изменении.
- Файлы голосовых и видеокружков загружаются/скачиваются по HTTP; WebSocket передаёт идентификаторы и метаданные.
- События публикуются после фиксации данных; возможны повторы и приход события раньше `command.result`.
- Сообщения объединяются по ID и сортируются по `seq`; версии сообщения, карточки и сводки сравниваются только внутри соответствующей сущности.
- Во время начальной HTTP-загрузки события буферизуются и затем объединяются с ответом по ID и версиям.
- После reconnect клиент обновляет сводку, карточки и загруженные диапазоны переписки; один `after_seq` не восстанавливает старые редактирования и удаления.

До реализации отдельно закрепить лимиты текста/медиа, временные ограничения редактирования и окончательные правила удаления. Список HTTP-чата и загрузка вложений также требуют завершения OpenAPI.
