# Деплой из GitHub Actions

Используются один `docker-compose.microservices.yml` и один shell-скрипт
`scripts/deploy/deploy.sh`.

## Что происходит при запуске

1. GitHub запускает существующий workflow тестирования.
2. Собирает Auth, Profile, Matching, Chat и Gateway и отправляет образы в GHCR.
   Тег каждого образа — полный SHA коммита.
3. Загружает код и семь env-файлов в `~/app/releases/<SHA>/` на сервере.
4. Поднимает хранилища в постоянном проекте `totallyswipes-microservices`,
   применяет миграции и `grants.sql`.
5. Запускает пять новых приложений в проекте `totallyswipes-<первые 12 символов SHA>`.
   Это позволяет проверить новую версию до остановки предыдущей.
6. Ждёт готовности контейнеров: gRPC Health Check и `/health` Gateway.
7. Проверяет nginx-конфиг, переключает его на новый Gateway и проверяет через HTTPS,
   что отвечает именно новый SHA.
8. Сохраняет имя активного проекта в `~/app/current-project` и останавливает
   предыдущие приложения. PostgreSQL, Redis, MinIO и volumes не останавливаются
   и не удаляются этим шагом.

Если возникает ошибка до переключения, предыдущие приложения остаются работать.
При ошибке после изменения nginx скрипт восстанавливает прежний конфиг и reload.
Если восстановление nginx завершилось ошибкой, новый комплект тоже сохраняется
для диагностики. После успешного переключения сначала останавливается прежний
Gateway, затем остальные приложения: WebSocket-клиенты должны переподключиться.

Образы и контейнеры прежних приложений сохраняются, но приложения остановлены.
Два комплекта временно требуют дополнительной памяти. При повторном запуске того же
SHA используется тот же Compose-проект.

Если ошибка возникла уже при остановке прежних контейнеров, новая версия остаётся
активной, а workflow завершается с ошибкой. В этом случае оставшиеся старые приложения
нужно остановить вручную; хранилища не трогать.

## Первая установка

Первый переход вы выполняете полным перезапуском. Остановку неизвестных контейнеров
скрипт не пытается угадать. Перед первым запуском workflow:

- Подготовить PostgreSQL: миграции, роли и пароли из основной инструкции README.
- Подготовить MinIO: bucket и пользователей либо учётные данные для локального запуска.
- Остановить прежние контейнеры, занимающие 80/443. Без `--volumes` данные сохраняются.
- Положить сертификаты в `~/app/certs/fullchain.pem` и `~/app/certs/privkey.pem`.
- Запустить фронтенд в сети `totallyswipes-edge`, alias `frontend`, внутренний порт 80.

Имена volumes постоянного проекта совпадают с ручным запуском
`docker-compose.microservices.yml`. Данные прежнего монолита автоматически не
переносятся: если у него другие volumes или структура хранения, перед переходом
нужно отдельно перенести данные в подготовленные хранилища. Скрипт старые volumes
не удаляет и не подключает их одновременно ко второму PostgreSQL.

На сервере нужны Docker, Compose 2.30+, Bash, curl, rsync и flock. Пользователь SSH
должен иметь доступ к Docker. Каталог приложения — `~/app`. Порты приложений наружу
не публикуются: публичный вход — nginx, контейнер `totallyswipes-nginx`.

## Secrets и Variables в GitHub

В Settings → Secrets and variables → Actions задать Secrets:

| Secret | Значение |
| --- | --- |
| `SSH_PRIVATE_KEY` | SSH-ключ сервера |
| `SSH_KNOWN_HOSTS` | Проверенный known_hosts сервера |
| `SSH_HOST` | Адрес сервера |
| `AUTH_ENV` | Содержимое `deploy/env/auth.env` |
| `PROFILE_ENV` | Содержимое `deploy/env/profile.env` |
| `MATCHING_ENV` | Содержимое `deploy/env/matching.env` |
| `CHAT_ENV` | Содержимое `deploy/env/chat.env` |
| `GATEWAY_ENV` | Содержимое `deploy/env/gateway.env` |
| `POSTGRES_ENV` | Содержимое `deploy/env/postgres.env` |
| `MINIO_ENV` | Содержимое `deploy/env/minio.env` |

Все секреты должны содержать заполненные значения, а не `replace-*`. Auth и Gateway
используют один JWT_SECRET. Пароли PostgreSQL/MinIO должны совпадать с подготовленными
хранилищами. Env передаётся как данные, без исполнения в shell.

Опциональные Variables:

| Variable | По умолчанию | Назначение |
| --- | --- | --- |
| `SSH_USER` | `ubuntu` | Пользователь сервера |
| `PUBLIC_HOST` | `totallyswipes.ru` | Домен HTTPS-проверки; также должен быть настроен в nginx и сертификате |
| `LEGACY_PROJECT` | `app` | Имя прежнего Compose-проекта при первом деплое |

Если прежний монолит работает в проекте `app`, после успешного первого деплоя
останавливается только его `api`. Если прежние микросервисы запускались вручную
в проекте `totallyswipes-microservices`, задать это имя в `LEGACY_PROJECT`:
останавливаются только `auth/profile/matching/chat/gateway`. После первого успешного
деплоя предыдущий проект определяется по `~/app/current-project`.
Наличие старого работающего приложения не обязательно: после полного первого
перезапуска отсутствие старых контейнеров допустимо.

## Как запустить

В GitHub открыть Actions → **Deploy microservices** → Run workflow и выбрать `dev3`
или нужный тег. Деплой запускается вручную. Push и PR запускают проверку кода.

Сервер загружает образы по SHA; на сервере Go-код не собирается. Не перезаписывать
уже выпущенные SHA-теги образов. Полное обновление инфраструктурных образов требует
отдельного обслуживания хранилищ; обычный релиз приложения их версии не меняет.

Для ручного запуска того же сценария после загрузки кода и env:

```bash
bash "$HOME/app/releases/<SHA>/scripts/deploy/deploy.sh" \
  "$HOME/app" ghcr.io/go-park-mail-ru/2026_2_totallyswipes <SHA>
```

## Ограничения

Миграции выполняются при работающей предыдущей версии: они должны быть совместимы
со старым кодом. Восстановление nginx не откатывает схему или данные БД.

Chat использует брокер в памяти. При смене версии прежние WebSocket закрываются,
поэтому фронтенд должен переподключиться и обновить историю/счётчики. Непрерывная
доставка событий между разными экземплярами сейчас не гарантируется.

Healthcheck проверяет доступность процесса и завершение начальной инициализации.
Это не полноценная проверка пользовательских сценариев.
